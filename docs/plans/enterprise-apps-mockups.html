Plan: migrate enterprise applications

Movewise feature proposal · revision 2: a separate Applications section, linked to policy migration · for review before any code is written

1. Goal

Today, apps are only a dependency of policies: when a Conditional Access policy names an app, Movewise matches it by app ID, and if the destination doesn't have it, the admin is told to add it by hand. This feature adds an Applications section of its own, with its own steps, that migrates enterprise applications and app registrations with their settings, sign-on and user and group assignments. The policy migration stays as it is, and the two are linked so policies find the apps migrated for them.

2. Decisions

Structure: a separate Applications section in the sidebar, with its own flow (Choose apps → Map users & groups → Pre-flight → Deploy). It uses the tenants signed in on Connect. The policy flow (Discover, Map, Pre-flight, Deploy) doesn't change, apart from recognising migrated apps.
Scope: enterprise apps (gallery and multi-tenant apps, same app ID in every tenant) and the source's own app registrations (recreated with a new app ID). Microsoft's first-party apps and managed identities are left out.
API permissions: copied onto the app, but admin consent is never granted by Movewise. They're listed for an admin to grant.
SAML single sign-on: migrated, with a new signing certificate (the old private key can't be exported). The results list each SAML app whose vendor side needs the new certificate or metadata.

3. How the two flows link

SituationWhat Movewise does
Apps migrated first (recommended order)Each run records source app ID → destination app ID for the destination tenant. The policy Map screen reads it: an app registration recreated with a new app ID matches automatically as Migrated by Movewise, and the policies are rewritten with the new ID.
A policy needs an app that isn't in the destinationThe policy Map entry says "Not in the destination yet" with a Migrate it in Applications link that opens the Applications section with that app already ticked.
Policies deployed before their appsPre-flight warns which policies point at apps still missing, so they're not created pointing at nothing.
Apps only, no policy migrationFully supported: the Applications section works on its own, for example to move just the SSO apps.

6. How it's built

AreaChange
ScreensA new Applications sidebar item with four pages (choose, map, pre-flight, deploy) and its own step bar. The pages reuse the existing table, mapping and pre-flight components, so they look and behave like the policy flow.
StateIts own state, separate from the policy migration's, so the two never overwrite each other's selection or mapping. Both use the tenants signed in on Connect.
RegistryTwo new types used only by this section: enterpriseApp (v1.0/servicePrincipals, leaving out Microsoft first-party apps and managed identities) and appRegistration (v1.0/applications). References: owners, assigned users and groups.
ExportRead each app with its appRoleAssignedTo, owners, SSO settings, claims mapping policy and, for registrations, the full manifest. Record what can't be copied for "Set up by hand".
App ID mapNew: each app run saves source app ID → destination app ID for the destination tenant, next to its run files. The policy Matcher checks it before reporting an app as missing.
Pre-flightNew findings: consent needed, new SAML certificate, secrets to recreate, provisioning by hand, apps already there (skip or update in place), unmatched users and groups. Role check: Application Administrator or Cloud Application Administrator. In the policy flow: a warning for policies pointing at apps still missing.
DeployThe existing engine, as its own run kind: apps (gallery apps through applicationTemplates/{id}/instantiate, others by creating the service principal or registration) → SSO settings and new certificate → owners and assignments. Progress saved after each step, resumable.
RollbackDeletes the apps and assignments the run created (deleted apps stay restorable for 30 days in Entra ID), puts back settings it changed on existing apps, and removes its entries from the app ID map.
Compare & driftApps can be included in comparisons and snapshots: an assignment removed or an SSO setting changed shows up as drift.
DemoContoso gets sample apps (a gallery SAML app, a multi-tenant app, two app registrations) so the whole flow, and the link to policies, can be tried.
TestsCore tests with the fake Graph: export, deploy order, app ID map written and read by the policy Matcher, rollback, and that consent is never granted.

7. Phases

  1. Applications section + enterprise apps: sidebar item, four steps, enterprise apps (same app ID) with settings, owners and assignments, rollback, demo, tests.
  2. App registrations + the link: recreate with a new app ID, the app ID map, "Migrated by Movewise" and "Migrate it in Applications" on the policy Map screen, permissions listed, secrets under "Set up by hand".
  3. SAML SSO: SSO settings and claims, new signing certificate, gallery-template instantiation.
  4. Docs and site: README, a website page "Migrate enterprise applications between tenants", release notes.

Each phase ships on its own and is tested in the demo before the next.

8. Risks

  • Gallery templates: some gallery apps can't be instantiated by template; those fall back to "Set up by hand" with the template name.
  • Hard-coded app IDs: scripts, daemons or mobile apps that hard-code an app registration's old app ID keep pointing at the source. The results list every new app ID.
  • Order: if the policies are migrated before the apps, they can't point at apps that don't exist yet. Pre-flight warns, and the policy Map links straight to Applications.
